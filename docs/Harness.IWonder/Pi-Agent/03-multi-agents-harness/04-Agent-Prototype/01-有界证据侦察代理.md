# 有界证据侦察代理

> [!abstract]
> Scout 是面向有限问题集的只读证据收集器：它在 Contract Scope 与硬预算内执行搜索、阅读和调用链追踪，通过结构化 Observation 更新 Evidence Table，以连续低收益、问题覆盖、预算耗尽或外部阻塞作为收束条件，并用可验证的终止工具向 Lead 交付当前最佳结论与明确未知项。

> [!note]
> **上层主题：** [状态平面与代理通信协议](../04-状态协作层/01-状态平面与代理通信协议.md)  
> **下层主题：** [权限、收敛与验收机制](../06-治理验证层/01-权限收敛与验收机制.md)

## 1. 产品定位

### 1.1 Scout 负责

- 定位相关文件；
- 查找配置与默认值；
- 跟踪调用链；
- 收集文件与行号证据；
- 回答 Contract Questions；
- 标记尚未确认项；
- 提交候选原因。

### 1.2 Scout 不负责

- 设计完整解决方案；
- 修改生产代码；
- 扩大产品范围；
- 消灭所有未知；
- 决定追加预算；
- 宣告全局目标完成。

### 1.3 Scout 终态

- `EVIDENCE_READY`；
- `BUDGET_EXHAUSTED`；
- `BLOCKED`。

## 2. Scout Contract

```yaml
task_id: scout-auth
contract_version: 1

objective:
  定位本次登录超时问题可能涉及的代码路径

scope:
  include:
    - src/auth/**
    - tests/auth/**
  exclude:
    - UI 样式
    - 密码策略重构
    - 与登录超时无关的历史缺陷

questions:
  - id: timeout-definition
    text: 超时值在哪里定义？
  - id: session-refresh
    text: 哪些路径会刷新 session？
  - id: default-consistency
    text: 是否存在不一致的默认值？

deliverables:
  - 相关文件和行号
  - 调用链
  - 有证据支持的候选原因
  - 未确认项

budget:
  max_exploration_calls: 12
  max_files_read: 20
  max_minutes: 10

stop_when:
  - 所有问题均 answered 或 unknown
  - 连续两个 observation cycle 没有高价值增量
  - 任一硬预算耗尽
  - 遇到外部阻塞
```

## 3. Scout Runtime 装配

### 3.1 Role Prompt

Role Prompt 只定义稳定行为：

- Evidence First；
- Question-driven Search；
- Scope Discipline；
- Unknown Allowed；
- Structured Finalization。

Contract 作为独立输入注入，不将每次任务事实写死在 Role Prompt。

### 3.2 Active Tools

推荐最小工具面：

```text
scout_search
scout_read
record_observation
record_evidence
submit_scout_report
```

可选保留 Pi Built-in：

```text
read
grep
find
ls
```

不默认提供：

- `write`；
- `edit`；
- 无约束 `bash`；
- Worker 与 Reviewer Tools；
- Lead Control Tools。

### 3.3 为什么包装搜索工具

自定义 `scout_search` 与 `scout_read` 可以统一产生：

- `observation_id`；
- Canonical Path；
- Touched Files；
- Scope Validation；
- Budget Accounting；
- Truncation Metadata；
- Query Fingerprint。

直接开放 Bash 难以可靠限制访问路径和统计文件。

## 4. 证据循环

```text
Select unresolved question
  ↓
Perform one bounded exploration batch
  ↓
Receive observation_id
  ↓
Assess relevance
  ├─ accepted evidence
  ├─ useful lead
  └─ low yield
  ↓
Commit observation
  ↓
Update Evidence Table and budgets
  ↓
Evaluate stop conditions
```

> [!revision]
> **2026-08-28 · 经验修订**
>
> 基于 [失败轨迹](../00-Artifact/20260828-2-多代理协作能力研究札记——一次失败经历的复盘.md) 与 [经验验证](../09-经验验证层/01-失败轨迹与知识修订.md)，原“每 Turn 只允许一个探索动作”因可能放大串行认知税，修订为“有界探索批次 + 批次级 Observation Commit”。

### 4.1 有界探索批次

原先“每 Turn 只允许一个探索动作”的约束会放大串行 Turn 成本，并可能使 Scout 为完成一个搜索—阅读链路产生过多轮次；修订后允许一个有界批次包含少量相互独立的 Search 或 Read，但批次结束后必须统一提交 Observation。

批次规则：

- 每批最多 2—3 个探索调用；
- 依赖前一结果的调用保持串行；
- Sibling Call 在 `tool_call` preflight 原子计入预算；
- 每批只生成一个 Yield Outcome；
- Pending Batch 未 Commit 前禁止下一批；
- 并行度由 Contract 声明而非模型自行扩大。

### 4.2 Pending Observation Gate

上一探索批次的 Observation 未 Commit 前，下一批探索动作被拒绝：

```text
observation pending
  ├─ record_evidence
  ├─ mark_useful_lead
  └─ mark_low_yield
```

该门禁把“搜索后是否产生价值”的判断变成显式协议。

## 5. Evidence Table

### 5.1 Question View

| Question | Status | Evidence | Confidence |
| :-- | :-- | :-- | :-- |
| timeout-definition | answered | ev-01 | high |
| session-refresh | answered | ev-02, ev-03 | medium |
| default-consistency | unknown | ev-04 | low |

### 5.2 Evidence Record

```json
{
  "evidence_id": "ev-01",
  "question_ids": ["timeout-definition"],
  "claim": "登录超时默认值为 30 秒",
  "path": "src/auth/session.ts",
  "line_start": 41,
  "line_end": 44,
  "excerpt": "const LOGIN_TIMEOUT = 30_000",
  "kind": "verified",
  "confidence": "high"
}
```

### 5.3 Evidence Kind

- `lead` 表示值得继续验证的线索；
- `verified` 表示引用支持当前 Claim；
- `contradicted` 表示引用否定已有 Claim。

### 5.4 Unknown

Unknown 必须包含：

- 已搜索范围；
- 未找到的事实；
- 现有弱证据；
- 继续确认所需条件；
- 是否建议追加预算。

Unknown 是合法结论，不触发无限搜索。

## 6. Low-Yield 机制

### 6.1 高价值增量

一个 Cycle 只有满足下列条件之一才清零 Low-Yield Streak：

- 新增关联未解决 Question 的 Accepted Evidence；
- 新增可验证调用边；
- 排除一个主要候选原因；
- 将 Question 从 Unknown 推进为 Answered；
- 发现需要 Lead 批准的明确 Scope Boundary。

### 6.2 低收益结果

下列情况增加 Low-Yield Streak：

- 重复已有搜索；
- 只发现无关文件；
- 新信息无法关联任何 Question；
- 没有新增 Lead、Evidence 或排除项；
- 探索明显偏离 Scope。

### 6.3 停止规则

```ts
if (acceptedEvidenceAdded) {
  lowYieldStreak = 0;
} else {
  lowYieldStreak += 1;
}

if (lowYieldStreak >= 2) {
  transitionToFinalizing("TWO_CONSECUTIVE_LOW_YIELD_CYCLES");
}
```

## 7. Budget 模型

### 7.1 Exploration Budget

计入：

- Search；
- Read；
- Trace；
- 其他访问仓库的探索动作。

不计入：

- `record_observation`；
- `record_evidence`；
- `submit_scout_report`；
- Runtime 内部 Telemetry。

### 7.2 File Budget

`max_files_read` 统计实际读取内容的唯一 Canonical Path；Search 结果中只出现文件名但未读取正文时，不计入 Read Budget。

### 7.3 Time Budget

- Soft Deadline 触发 Finalize；
- Hard Deadline 触发 Abort；
- Finalization 拥有独立保留时间；
- Provider Retry 消耗墙钟时间。

### 7.4 Budget Exhaustion

```text
budget reached
  ↓
RUNNING → FINALIZING
  ↓
disable scout_search / scout_read
  ↓
commit pending evidence
  ↓
submit BUDGET_EXHAUSTED report
```

## 8. Scope Guard

### 8.1 Path Scope

- Read Path 必须匹配 Include Glob；
- Excluded Path 优先拒绝；
- Symlink 解析为 Canonical Path 后校验；
- Relative Path 基于固定 Run CWD 解析。

### 8.2 Semantic Scope

Path 合法但 Query 与 Questions 无关时记录 Scope Drift；连续 Scope Drift 可触发 Low-Yield 或 Lead Warning。

### 8.3 Bash Policy

Scout 默认不使用 Bash；确需 Bash 时仅开放封装后的只读命令模板，不依赖 Prompt 自觉保持只读。

## 9. Finalization Gate

### 9.1 进入条件

- 所有 Questions 已 Answered 或 Unknown；
- 连续两个 Low-Yield Cycle；
- 任一 Hard Budget Exhausted；
- Lead 发出 Finalize；
- 外部 Blocker 已确认。

### 9.2 Finalizing 工具面

保留：

- `record_observation`；
- `record_evidence`；
- `submit_scout_report`。

关闭：

- `scout_search`；
- `scout_read`；
- `scout_trace`。

## 10. Structured Terminal Report

```ts
interface ScoutReport {
  taskId: string;
  runId: string;
  contractVersion: number;
  terminalStatus:
    | "EVIDENCE_READY"
    | "BUDGET_EXHAUSTED"
    | "BLOCKED";
  questionResults: QuestionResult[];
  evidenceIds: string[];
  callChain: CallEdge[];
  candidateCauses: CandidateCause[];
  unknowns: UnknownRecord[];
  budget: BudgetSnapshot;
  stopReason: string;
}
```

### 10.1 Report Validation

`submit_scout_report` 校验：

- 每个 Question 均有结果；
- Answered 结果引用 Accepted Evidence；
- Evidence ID 存在；
- EVIDENCE_READY 满足 Coverage；
- BUDGET_EXHAUSTED 对应真实预算事件；
- BLOCKED 包含外部条件与解除动作；
- Contract Version 与 Run 一致。

### 10.2 Termination

验证成功后：

- 保存 Scout Report Artifact；
- 更新 Run Business Status；
- 返回 Tool Result `terminate: true`；
- 通知 Lead `RUN_COMPLETED`；
- Task 进入 Completed 而非 Verified。

## 11. Context Capsule 与下游交接

### 11.1 Scout Context Capsule

Terminal Report 同时生成 Context Capsule，包含 Source Scope、Files Read、Verified Claims、Rejected Hypotheses、Decisions、Constraints、Unknowns、Confidence 与 Content Hash。

### 11.2 Handoff ACK

Planner、Worker 或 Reviewer 启动后先声明：

- 已接受 Artifact；
- 已接受 Claims；
- 拒绝的 Claims；
- 尚存 Context Gaps；
- 允许追加读取的范围。

### 11.3 Context Gap Gate

下游不能因为“不放心”重新执行全量 Recon；额外探索必须绑定 Context Gap、Acceptance Criterion、Evidence Verification Failure 或 P0/P1 风险。

### 11.4 独立性策略

Worker 优先复用 Verified Capsule；Reviewer 可以抽样复核；需要避免锚定的独立 Reviewer 可延迟接收 Candidate Cause，但仍接收 Scope、Acceptance 与文件清单。

## 12. Lead 调控点

Lead 可以：

- 查询 Question Coverage；
- 查询 Remaining Budget；
- 缩小 Scope；
- 批准追加预算；
- 要求 Finalize；
- 接受 Unknown；
- Abort 失控 Run。

Scout 不可以：

- 自行追加预算；
- 自行改变 Questions；
- 自行扩展 Write Scope；
- 自行宣告 Goal Achieved。

## 13. 原型验收标准

Scout 原型至少证明：

1. 不同 Scout Run 拥有独立 AgentSession；
2. Scout 看不到 Edit、Write 与 Lead Tools；
3. Scope 外 Read 在执行前被拒绝；
4. Tool、File 与 Time Budget 可观察；
5. 单个探索批次受到并发上限与预算约束；
6. Pending Batch Observation 阻止下一批探索；
7. 连续两个 Low-Yield Cycle 触发 Finalize；
8. Budget Exhausted 仍能提交报告；
9. Final Report 通过 Schema 与 Evidence Validation；
10. Lead 可 Status、Finalize 与 Abort；
11. Scout 产出可验证 Context Capsule；
12. 下游必须 Handoff ACK 后才能追加探索。

## 14. Scout 产品原则

- Scout 对问题集负责。
- Scout 不对无限知识负责。
- Evidence 优先于叙述。
- Unknown 优先于无止境搜索。
- Budget 由 Harness 强制。
- 追加预算由 Lead 决定。
- Finalization 是独立阶段。
- Agent 完成仍需系统验证。
- Scout 输出必须能被下游接受和复用。
- 上下文隔离收益以 Artifact Reuse 衡量。
