# Pi 拓展运行时基础

> [!abstract]
> Pi 已经开放了构建多代理 Harness 所需的主要控制点：Extension 负责事件拦截与能力注册，ResourceLoader 负责角色资源装配，AgentSession 负责上下文与运行隔离，Active Tools 负责模型能力披露，Session Entry 负责状态恢复，SDK 与 RPC 负责子代理控制；`pi-subagents` 的核心工作是在这些原语之上建立角色边界、生命周期协议和受控 Capability，而非修改 Pi 核心 Agent Loop。

> [!note]
> **上层主题：** [多代理支撑系统知识树](../00-总览层/00-多代理支撑系统知识树.md)  
> **下层主题：** [多代理支撑系统架构](../02-支撑系统架构层/01-多代理支撑系统架构.md)

## 1. 本层回答的问题

Pi 拓展支撑层需要回答六个基础问题：

1. Extension 能在哪些生命周期节点观察或改变运行行为？
2. Runtime 能力如何以受控 Tool Schema 暴露给 Agent？
3. 不同角色如何获得不同的 Tools、Hooks、Prompt 与 Skills？
4. 子代理如何建立独立 Context、Session 与进程边界？
5. Lead 如何向运行中的 Subagent 发送控制消息？
6. Session reload、fork 与 shutdown 后状态如何恢复或清理？

本层只讨论 Pi 已提供的运行时原语，不定义上层 Task DAG、Scout Contract 与验收流程。

## 3. Extension 的加载与作用域

### 3.1 Extension Factory

Extension 是接收 `ExtensionAPI` 的 TypeScript Factory：

```ts
export default function extension(pi: ExtensionAPI) {
  pi.on("session_start", (_event, ctx) => {
    ctx.ui.notify("runtime ready", "info");
  });

  pi.registerTool({
    name: "runtime_status",
    label: "Runtime Status",
    description: "Read a sanitized runtime snapshot",
    parameters: Type.Object({}),
    async execute(_id, _params, _signal, _onUpdate, ctx) {
      return {
        content: [{
          type: "text",
          text: JSON.stringify({
            sessionId: ctx.sessionManager.getSessionId(),
            model: ctx.model?.id,
          }),
        }],
        details: {},
      };
    },
  });
}
```

Factory 在资源加载期注册静态能力；长期进程、Socket、Watcher 与 Timer 应推迟到 `session_start` 或实际 Tool 调用后创建。

### 3.2 Extension 是功能加载边界

Extension 加载后，其 Hooks、Commands 与共享状态进入当前 Runtime；即使某个 Tool 未激活，Extension 中注册的 `tool_call`、`context` 或 `session_shutdown` Handler 仍然存在。

因此：

- Tool Activation 只能控制模型可见工具；
- Extension Selection 才能控制 Hook 与副作用集合；
- Role Isolation 应优先建立在 ResourceLoader 上；
- `setActiveTools()` 适合同一角色内部的渐进能力披露。

### 3.3 Package 不是 Agent 能力边界

一个 Package 可以包含多个 Extension、Skill 与内部模块；Package 只负责分发，最终加载哪些模块由 ResourceLoader 与入口路由决定。

```text
Package
  └─ Extension Entry
      └─ Role Module
          └─ Tool Registry
              └─ Active Tools
```

## 4. Pi 生命周期开放点

### 4.1 Session 生命周期

```text
project_trust
  ↓
session_start
  ↓
resources_discover
  ↓
agent runs
  ↓
session_shutdown
```

关键事件：

| Event | Harness 用途 |
| :-- | :-- |
| `project_trust` | 决定是否接受项目级 Agent 与 Extension 配置 |
| `session_start` | 恢复 Supervisor 纯数据状态并建立 Session 资源 |
| `resources_discover` | 注入角色级 Skill、Prompt 与 Theme |
| `session_before_switch` | 在 new 或 resume 前处理活跃 Child |
| `session_before_fork` | 决定 Child Run 是否允许跟随会话分支 |
| `session_shutdown` | Abort Child、关闭传输、清理 Timer 与 Watcher |

### 4.2 Agent 生命周期

```text
before_agent_start
  ↓
agent_start
  ↓
turn_start ↔ turn_end
  ↓
agent_end
  ↓
agent_settled
```

`agent_end` 只表示一次低层运行结束，之后仍可能发生自动重试、上下文压缩重试或 queued continuation；只有 `agent_settled` 表示 Pi 不会自动继续运行。

### 4.3 Tool 生命周期

```text
tool_execution_start
  ↓
tool_call
  ├─ mutate input
  ├─ allow
  └─ block
  ↓
tool execution
  ↓
tool_result
  ↓
tool_execution_end
```

Harness 映射：

- Scope Guard 放在 `tool_call`；
- Tool Budget 在 `tool_call` 原子计数；
- 实际文件与结果统计放在 `tool_result`；
- Tool Telemetry 通过 execution events 观察；
- Tool Result 可携带分支可恢复的 `details`。

### 4.4 并行 Tool Call 约束

Pi 默认允许同一 Assistant Message 发出多个 Tool Call；preflight 按源码顺序执行，实际执行可以并发。

Scout 需要在 `turn_start` 重置计数，并在 `tool_call` 阻止同一 Turn 过多探索：

```ts
let explorationCallsThisTurn = 0;

pi.on("turn_start", () => {
  explorationCallsThisTurn = 0;
});

pi.on("tool_call", event => {
  if (!isExplorationTool(event.toolName)) return;

  explorationCallsThisTurn += 1;
  if (explorationCallsThisTurn > 1) {
    return {
      block: true,
      reason: "Commit the current observation before another exploration call.",
    };
  }
});
```

## 5. Runtime 能力面

### 5.1 ExtensionAPI 的主动修改能力

| API | 修改对象 |
| :-- | :-- |
| `pi.setActiveTools()` | 当前模型可调用工具集合 |
| `pi.setModel()` | 当前模型 |
| `pi.setThinkingLevel()` | 当前推理级别 |
| `pi.sendMessage()` | Extension 消息与 LLM Context |
| `pi.sendUserMessage()` | 用户消息与新 Turn |
| `pi.appendEntry()` | 不进入 LLM Context 的持久状态 |
| `pi.setSessionName()` | Session 展示元数据 |

### 5.2 ExtensionContext 的运行控制能力

| API | 控制语义 |
| :-- | :-- |
| `ctx.abort()` | 中止当前 Agent Operation |
| `ctx.compact()` | 请求 Context Compaction |
| `ctx.shutdown()` | 请求 Pi 优雅关闭 |
| `ctx.isIdle()` | 判断 Runtime 是否完全空闲 |
| `ctx.getContextUsage()` | 查询当前 Context 使用量 |
| `ctx.getSystemPrompt()` | 查询当前 System Prompt |

### 5.3 事件返回值修改点

| Event | 修改能力 |
| :-- | :-- |
| `before_agent_start` | 替换 System Prompt 或注入消息 |
| `context` | 替换发送给模型的 Messages |
| `tool_call` | 修改 Input 或 Block |
| `tool_result` | 修改 Content、Details、Usage 与错误状态 |
| `message_end` | 替换同 Role 的最终消息 |

## 6. Runtime 能力如何暴露给 Agent

### 6.1 Raw Context 不进入 Agent

Agent 不应获得：

- 原始 `ExtensionAPI`；
- 原始 `ExtensionContext`；
- `SessionManager` 写能力；
- Child Process Handle；
- Credential 与 Model Registry 内部对象；
- 其他 Run 的可变引用。

### 6.2 Capability Tool

需要 Agent 主动决定的操作才注册 Tool：

```text
Lead-visible
  ├─ subagent_start
  ├─ subagent_status
  ├─ subagent_control
  └─ subagent_collect

Scout-visible
  ├─ scout_search
  ├─ scout_read
  ├─ record_evidence
  └─ submit_scout_report
```

自动执行的约束保持为隐藏 Hook：

```text
Hidden Policy
  ├─ Scope Guard
  ├─ Budget Guard
  ├─ Low-Yield Accounting
  ├─ Finalization Gate
  └─ Session Cleanup
```

### 6.3 Capability 设计规则

- Query 与 Mutation 分离；
- 控制动作使用有限 Enum；
- Mutation 携带 `expected_version`；
- Tool Result 返回 sanitized snapshot；
- Snapshot 返回当前 `allowed_actions`；
- 非法状态转换由 Runtime 拒绝；
- Infrastructure Abort 与 Business Finalize 分离。

## 7. Tool Registry 与 Active Tools

### 7.1 Registry 语义

Tool Registry 包含：

- Built-in Tools；
- Extension `registerTool()` 注册工具；
- SDK `customTools` 注入工具；
- Runtime 期间动态加入的工具。

Registry 表示 Runtime 已知能力，不表示模型当前可见能力。

### 7.2 Active Tools 语义

`tools`、`excludeTools` 与 `pi.setActiveTools()` 共同决定模型当前收到的 Tool Definitions。

```ts
pi.setActiveTools([
  "read",
  "grep",
  "find",
  "record_evidence",
  "submit_scout_report",
]);
```

### 7.3 动态工具加载

Pi 支持在 Tool 执行后增量激活新工具；适用场景是 Scout 发现认证问题后加载 `auth_trace`，不适合在同一 Runtime 中把 Scout 切换为 Worker。

原因：

- 角色 Hooks 已经加载；
- 角色内部状态可能串扰；
- 权限边界难以审计；
- System Prompt 语义发生角色漂移。

## 8. Role ResourceLoader

### 8.1 精确装配

`DefaultResourceLoader` 支持禁用默认发现并显式加入角色资源：

```ts
const loader = new DefaultResourceLoader({
  cwd,
  agentDir,

  noExtensions: true,
  additionalExtensionPaths: [
    commonPolicyExtension,
    scoutExtension,
  ],

  noSkills: true,
  additionalSkillPaths: [scoutSkill],

  noContextFiles: true,
  systemPromptOverride: () => scoutSystemPrompt,
  appendSystemPromptOverride: () => [],
});

await loader.reload();
```

### 8.2 角色 Session

```ts
const { session } = await createAgentSession({
  cwd,
  resourceLoader: loader,
  tools: [
    "read",
    "grep",
    "find",
    "record_evidence",
    "submit_scout_report",
  ],
  sessionManager: SessionManager.inMemory(cwd),
});
```

每个角色由以下装配式决定：

```text
Agent Context
  = Role Prompt
  + Task Contract
  + Stable Project Instructions
  + Dependency Artifacts
  + Relevant Skills
  + Active Tool Definitions
  + Runtime Policy
```

## 9. Prompt、Context 与 Skill

### 9.1 Prompt 来源

Pi Prompt 可能来自：

- 默认 System Prompt；
- 全局或项目 `SYSTEM.md`；
- `APPEND_SYSTEM.md`；
- CLI `--system-prompt` 与 `--append-system-prompt`；
- `before_agent_start` 动态修改；
- Context Files 与 Skill 描述。

### 9.2 `systemPromptOptions`

`before_agent_start` 可读取：

- `selectedTools`；
- `toolSnippets`；
- `promptGuidelines`；
- `contextFiles`；
- `skills`；
- `appendSystemPrompt`。

这使 Extension 能在不重复发现资源的情况下完成角色感知 Prompt 修改。

### 9.3 Skill 的真实语义

加载 Skill 只会把名称与描述放入 System Prompt；Agent 仍需读取 `SKILL.md`，或通过 `/skill:name` 显式展开。

因此：

- 可选工作流使用 Skill；
- 强制规则进入 Role Prompt 与 Runtime Policy；
- Skill 的 `allowed-tools` 不作为安全边界；
- Tool Allowlist 由 AgentSession 与 Extension Policy 决定。

## 10. Session Replacement 与持久化

### 10.1 Replacement 顺序

```text
session_before_switch / session_before_fork
  ↓
session_shutdown(old runtime)
  ↓
old runtime disposed
  ↓
new runtime created
  ↓
session_start(new runtime)
```

旧 Extension 实例、旧 `ctx` 与旧 SessionManager 在替换后均不可继续承担新 Session 操作。

### 10.2 可持久化状态

`pi.appendEntry()` 创建 Custom Entry，不进入 LLM Context，适合保存：

- Run Snapshot；
- Contract Revision；
- Last Seen Sequence；
- Budget Accounting；
- Artifact Reference；
- Supervisor 配置。

Tool Result `details` 适合保存跟随会话分支的工具状态。

### 10.3 不可持久化状态

以下对象只能存在于当前 Runtime：

- Child Process；
- AgentSession 实例；
- RPC Client；
- AbortController；
- Socket；
- Timer；
- Unsubscribe Function。

### 10.4 Shutdown Policy

- attached Child 在 `session_shutdown` 中终止；
- detached Child 转交外部 Durable Registry；
- reload 后从纯数据 Snapshot 重建 Handle；
- fork 不隐式复制活跃 Child Runtime。

## 11. JSON、RPC 与 SDK 传输

### 11.1 JSON Mode

官方 Subagent 示例通过 `spawn()` 启动 `pi --mode json -p --no-session`，并从 stdout 消费事件；该模式适合一次委派、一次返回，但示例将 stdin 设置为 ignore，无法提供持续双向监督。

### 11.2 RPC Mode

RPC 提供：

| Command | 生命周期意义 |
| :-- | :-- |
| `prompt` | 启动任务或立即执行 Extension Command |
| `steer` | 当前 Turn 工具结束后调整方向 |
| `follow_up` | Agent 完成后追加动作 |
| `abort` | 中止当前 Operation |
| `get_state` | 查询 Session 状态 |
| `get_messages` | 查询消息历史 |

### 11.3 SDK Mode

SDK 直接提供：

```ts
await session.prompt(contractPrompt);
await session.steer(controlMessage);
await session.followUp(finalizeMessage);
await session.abort();
const unsubscribe = session.subscribe(handleEvent);
```

### 11.4 选择原则

- 一次性侦察使用 JSON Mode；
- 强进程隔离与双向控制使用 RPC；
- 同进程精细控制使用 SDK；
- 跨语言宿主使用 RPC；
- `pi.events` 只用于共享 Event Bus，不跨 OS Process。

## 12. Pi-Subagents 支撑层结论

Pi 原生开放点已经足以实现角色化 Subagent Runtime：

```text
Extension
  提供 Hooks 与 Capability 注册

ResourceLoader
  提供角色资源装配

AgentSession
  提供上下文和运行隔离

Active Tools
  提供模型可见能力控制

Session Entry
  提供可恢复状态

SDK / RPC
  提供双向生命周期控制
```

`pi-subagents` 在该基础上还需补充：

1. Task、Run 与 Session 的三重状态模型；
2. Lead 的异步 Start、Status、Control、Collect API；
3. Evidence、Artifact 与 Mailbox 状态面；
4. Scope、Budget、Finalization 与 Verification Policy；
5. Scout、Planner、Worker 与 Reviewer 的角色模块；
6. Team 与 Workflow 的后续产品层。

## 13. 本层设计决策

- Extension 负责机制，Harness 负责秩序。
- Raw Runtime Context 仅在 Extension 内部存在。
- Agent 只获得 Schema 约束后的 Capability。
- 角色隔离优先使用独立 ResourceLoader 与 AgentSession。
- Active Tools 只解决模型可见性，不解决 Hook 隔离。
- Prompt 处理语义，Policy 处理不可违反规则。
- JSON 处理一次性委派，RPC 与 SDK 处理持续监督。
- Session Replacement 后必须重建所有 session-bound Handle。
