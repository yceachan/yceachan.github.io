## TL;DR

核心论点是A/ 的一篇技术博客的观点 : 多代理协作能力并不会随着模型智能提升而自然涌现。

## Background

近段时间，我在DSH 、Codex 、Pi with @nicobailon/pi-subagents 等Harness 上均尝试了以v4f /luna max 为主力模型的多代理编排工作流，效果惨不忍睹,最近的案例是[#1530](https://github.com/nicobailon/pi-subagents/issues/1530)。(原谅我AI灌水issue)。

矛盾在于：模型变强会让多代理系统更有用，但不会自动涌现出可靠的分工、通信、委派和冲突解决能力；这些仍然需要一个健壮的`multi agent harness`，提供可靠的上下文管理 和 交付边界机制。

### Introspection

两次多代理协同的trace，付出与收获均完全不成正比，此之谓慢工出烂活。

**多代理工作流达成目的耗时更长，这个论点表面看着具备显著性**，但它表征了核心矛盾：**多代理会重复性地反复探索工程上下文，这本质是一种试图用时空广度换取Correctness 的trade off**。

而更令我沮丧乃至绝望的是，如果伴随着一个较不完善的Harness (`Pi 社区 workflow`) 或较低智能的模型 (`luna max`)：

1. 主/子代理的上下文不共享，更多时候带来的不是**隔离工程噪音**，**保留Agent独立perspective** 这些**benefit** ， 而是在重复地为了解工程背景而付出同一份的认知税——所有执行者子代理认为**mustful and minial** 的基础上下文

    尽管已经编排了前置的Scout侦察，在#trace1的轨迹表明，Scout 输出的content 不被后阶段的代理们接纳，在他们的推理中，仍倾向于再次explore and read。而且`max`思考深度瞻前顾后的风格加剧了这一点。

    **trade off** 的平衡被打破了，我真的没有半点享受到隔离上下文的优越性，但付出了成倍不止的时间成本。

2. 对子代理的委派，相当依赖一个显式，明确的工作范围 和验收边界 收束，否则就会像#trace1一样发散

   - review从 package diff 扩展到 `.cache`、`.vscode`、`.codex`、imagegen skill 和其他无关内容。

## Addt

### 上下文隔离trade off

多代理协作里，“上下文隔离”本质是在权衡两件事：

> 让代理彼此独立，减少干扰；同时又要让它们掌握足够信息，避免重复劳动和方向错位。

可以把上下文看成代理的“工作记忆”。隔离程度不同，会形成三种典型模式。

| 模式       | 优点                             | 代价                             | 适合               |
| ---------- | -------------------------------- | -------------------------------- | ------------------ |
| 完全共享   | 协调简单、信息最全               | 噪声大、容易相互锚定、成本高     | 小团队、强耦合任务 |
| 完全隔离   | 独立判断、并行度高、隐私边界清晰 | 重复探索、容易理解偏差、整合困难 | 独立验证、竞争方案 |
| 选择性共享 | 平衡独立性与协作效率             | 需要设计交接协议                 | 大多数工程工作流   |

### benefit

**1. 减少上下文污染**

一个代理调试数据库问题时，不需要看到 UI 讨论、营销措辞或几十轮无关日志。隔离可以让它专注于局部目标，也降低注意力被错误线索占据的概率。

**2. 保留独立判断**

如果所有代理先看到同一个推测，比如“问题应该出在缓存”，它们很容易共同被锚定。隔离后，可以安排多个代理从不同假设出发，得到真正独立的复核结果。

这对代码审查、故障诊断和安全分析尤其重要。

**3. 控制成本和权限**

共享全部历史意味着更高的上下文消耗。更重要的是，不同代理可能只应看到各自需要的数据。例如支付代理无需接触用户聊天记录，文档代理也无需获得生产环境凭证。

**4. 提高并行度**

上下文边界明确后，任务更容易被拆成独立工作包，代理之间不必持续同步。

### price

**1. 信息损失**

代理可能不知道某个关键决定已经做过，于是：

- 重复调查；
- 推翻已有约束；
- 使用不兼容的假设；
- 修改了另一个代理正在依赖的接口。

隔离越强，委派说明就越需要完整。

**2. 隐含背景难以传递**

最难传递的往往不是“做什么”，而是：

- 为什么这样做；
- 哪些方案已经试过；
- 哪些约束不可妥协；
- 用户真正关心什么；
- 当前结论的置信度如何。

只转发最终结论，容易形成“信息压缩损失”。

**3. 整合成本上升**

两个代理各自交付正确结果，并不保证组合后仍然正确。例如前端按一种字段含义实现，后端按另一种含义实现，局部测试都可能通过，集成时才暴露问题。



上下文隔离并不是越强越安全。真正决定效果的是三个边界是否一致：

1. **认知边界**：代理知道什么；
2. **责任边界**：代理应该做什么；
3. **状态边界**：代理实际上能修改什么。

如果只隔离了认知，却共享可写状态，容易发生隐蔽冲突；如果只隔离权限，却没有明确责任，代理会互相等待；如果共享所有上下文，却没有所有权边界，则容易多人同时修改同一问题。

所以比较稳健的原则是：

> 默认隔离详细过程，显式共享目标、事实、接口、状态变化和验收标准；在需要独立判断时延迟共享结论，在需要集成时提高同步频率。
