# 任务、运行与会话生命周期

> [!abstract]
> 多代理系统同时存在业务任务、执行尝试和 Pi 会话三条生命周期：Task 表示应完成的业务责任，Run 表示一次可失败和重试的执行，Session 表示 Pi 的上下文与资源容器；Lead 通过异步控制 API 操作 Run，Harness 通过状态转换门禁维护三者一致性，并在业务终态与基础设施故障之间保留清晰边界。

> **上层主题：** [多代理支撑系统架构](../02-支撑系统架构层/01-多代理支撑系统架构.md)

## 1. 三条生命周期

### 1.1 Task Lifecycle

```text
PROPOSED
  ↓
READY
  ↓
CLAIMED
  ↓
RUNNING
  ├─ BLOCKED → READY / RUNNING
  ├─ FAILED  → RETRY / REASSIGN
  └─ COMPLETED
        ↓
      VERIFIED
        ↓
      INTEGRATED
```

状态语义：

| State | 定义 |
| :-- | :-- |
| `PROPOSED` | 已识别但尚未进入调度 |
| `READY` | 依赖已满足且具备 Contract |
| `CLAIMED` | 已分配 Owner 与 Lease |
| `RUNNING` | 至少一个 Run 正在执行 |
| `BLOCKED` | 外部条件阻止当前进展 |
| `FAILED` | 当前策略下无法产出有效交付 |
| `COMPLETED` | Agent 已提交声明完成的 Deliverable |
| `VERIFIED` | 验证机制确认 Deliverable 满足 Acceptance |
| `INTEGRATED` | 交付物进入目标状态或主工作区 |

### 1.2 Run Lifecycle

```text
CREATED
  ↓
STARTING
  ↓
RUNNING
  ├─ PAUSED ↔ RUNNING
  ├─ SATISFIED
  │     ↓ completion latch
  ├─ FINALIZING
  └─ ABORTING
        ↓
     TERMINATED
```

状态语义：

| Phase | 定义 |
| :-- | :-- |
| `CREATED` | Run Record 已建立 |
| `STARTING` | ResourceLoader、Session 或 Child Process 正在初始化 |
| `RUNNING` | Agent 正在执行 Contract |
| `PAUSED` | 当前 Turn 后禁止新探索 |
| `SATISFIED` | Required Acceptance 已满足并等待自动收束 |
| `FINALIZING` | 探索停止且只允许提交证据、集成产物与报告 |
| `ABORTING` | 基础设施终止正在进行 |
| `TERMINATED` | Run 不可继续执行 |

### 1.3 Pi Session Lifecycle

```text
startup
  ├─ reload
  ├─ new
  ├─ resume
  ├─ fork / clone
  └─ quit
```

Session Replacement 的典型顺序：

```text
before switch/fork
  ↓
session_shutdown(old runtime)
  ↓
old runtime disposed
  ↓
new runtime created
  ↓
session_start(new runtime)
```

## 2. 三条生命周期的关系

### 2.1 Task 与 Run

- 一个 Task 可拥有多个 Run；
- 一个 Run 只服务一个 Task Version；
- Retry 创建新 Run；
- Reassign 创建新 Owner 与 Run；
- Run Terminated 不自动改变 Task 为 Completed；
- Task Verified 不依赖原 Run 仍然存活。

### 2.2 Run 与 Session

- SDK 模式下一个 Run 绑定一个 AgentSession；
- RPC 模式下一个 Run 绑定一个 Child Pi Session；
- Session reload 会使 Runtime Handle 失效；
- Session fork 不自动复制 Child Process；
- Detached Run 需要外部 Supervisor 接管。

### 2.3 Task 与 Session

- Task ID 跨 Session 稳定；
- Session 只承载当前交互与本地状态；
- Task Registry 不应只存在于聊天 Context；
- Session Branch 不等于 Task Branch。

## 3. Lead 异步控制 API

### 3.1 为什么不能只用阻塞式 Tool

阻塞式 `subagent({ task })` 在 Child 完成前不返回，Lead LLM 无法调用其他控制工具；该模式适合一次性委派，不适合中途缩小 Scope、追加预算或要求收束。

### 3.2 Start

```ts
subagent_start({
  role: "scout",
  contract,
})
```

返回：

```json
{
  "run_id": "run-scout-auth-01",
  "task_id": "scout-auth",
  "phase": "STARTING",
  "version": 1,
  "allowed_actions": ["STATUS", "ABORT"]
}
```

Start 负责：

- 校验 Contract Schema；
- 创建 Run Record；
- 装配 Role Runtime；
- 启动 AgentSession 或 RPC Child；
- 立即返回 Run Handle ID。

### 3.3 Status

```ts
subagent_status({ run_id })
```

Snapshot 包含：

- Phase；
- Contract Version；
- Question Coverage；
- Evidence Count；
- Low-Yield Streak；
- Budget Used 与 Remaining；
- Last Progress；
- Blocker；
- Allowed Actions。

Snapshot 不包含：

- 原始 `ctx`；
- Child Process 对象；
- Credential；
- Socket；
- 其他 Run 的内部可变状态。

### 3.4 Control

```ts
subagent_control({
  run_id,
  command_id,
  expected_version,
  action,
  payload,
})
```

动作集合：

| Action | 语义 |
| :-- | :-- |
| `NARROW_SCOPE` | 缩小后续探索边界 |
| `ADD_QUESTION` | 通过 Contract Revision 增加问题 |
| `EXTEND_BUDGET` | 由 Lead 批准追加资源 |
| `PAUSE_AFTER_TURN` | 当前 Turn 后阻止新探索 |
| `RESUME` | 恢复 Paused Run |
| `FINALIZE` | 请求进入业务收束阶段 |
| `ABORT` | 立即中止基础设施运行 |

### 3.5 Collect

```ts
subagent_collect({
  run_id,
  wait_ms: 5000,
})
```

Collect 语义：

- 查询最终 Artifact；
- 可进行有界等待；
- 不修改 Run 状态；
- 对 Terminated Run 幂等；
- 未完成时返回 `ready: false`。

### 3.6 Handoff 与 Acceptance

Start、Status、Control、Collect 只覆盖 Run 监督，不保证下游采用上游结果；跨角色推进还需要 `handoff_context` 与 `ack_context`，记录 Producer Artifact、Consumer Run、Accepted Claims、Rejected Claims 与 Context Gaps。

## 4. Allowed Actions 作为状态机出口

每个 Snapshot 显式返回合法动作：

| Phase | Allowed Actions |
| :-- | :-- |
| `CREATED` | START、ABORT |
| `STARTING` | STATUS、ABORT |
| `RUNNING` | STATUS、NARROW_SCOPE、EXTEND_BUDGET、PAUSE_AFTER_TURN、FINALIZE、ABORT |
| `PAUSED` | STATUS、RESUME、FINALIZE、ABORT |
| `SATISFIED` | STATUS、FINALIZE、ABORT |
| `FINALIZING` | STATUS、ABORT |
| `ABORTING` | STATUS |
| `TERMINATED` | STATUS、COLLECT |

Agent 无需猜测状态机规则，非法 Transition 由 Supervisor 拒绝。

## 5. Finalize、Abort 与 Pause

### 5.1 Finalize

Finalize 是业务控制：

- 停止新的探索；
- 允许提交未提交 Evidence；
- 允许生成 Structured Report；
- 使用独立 Finalization Deadline；
- 成功后产生 Business Terminal Status。

### 5.2 Abort

Abort 是基础设施控制：

- SDK 调用 `session.abort()`；
- RPC 发送 `abort` Command；
- Process 最终可升级为 SIGTERM 与 SIGKILL；
- Abort 不保证产生完整业务报告。

### 5.3 Pause After Turn

Pi 没有原生 Pause Agent；Harness 实现 Turn Boundary Pause：

1. 当前 Provider Response 继续完成；
2. 已启动 Tool 继续完成；
3. 下一次探索 Tool 被 Policy Hook 阻止；
4. Run 等待 Resume、Finalize 或 Abort。

## 6. 业务终态与基础设施结果

### 6.1 Business Terminal Status

| Status | 定义 |
| :-- | :-- |
| `EVIDENCE_READY` | 问题集已形成可交付证据 |
| `BUDGET_EXHAUSTED` | 硬预算触发并提交当前最佳结论 |
| `BLOCKED` | 外部条件阻止完成 Questions |

### 6.2 Infrastructure Status

| Status | 定义 |
| :-- | :-- |
| `OK` | Runtime 正常结束 |
| `ABORTED` | Lead 或用户主动中止 |
| `TIMED_OUT` | Hard Deadline 触发 |
| `PROCESS_CRASHED` | Child 异常退出 |
| `PROTOCOL_ERROR` | RPC、Event 或 Schema 协议失败 |

一个 Run 可以同时具有：

```json
{
  "business_status": "BUDGET_EXHAUSTED",
  "infrastructure_status": "OK"
}
```

或仅有基础设施结果：

```json
{
  "business_status": null,
  "infrastructure_status": "PROCESS_CRASHED"
}
```

## 7. Budget Exhaustion 的正确路径

```text
hard budget reached
  ↓
RUNNING → FINALIZING
  ↓
disable exploration tools
  ↓
commit pending evidence
  ↓
submit best-current report
  ↓
TERMINATED
```

预算耗尽不应立即 Kill；Finalization Tool 不计入探索预算，并拥有保留时间。

## 8. Retry、Reassign 与 Recovery

### 8.1 Retry

- 新建 `run_id`；
- 保留 `task_id`；
- 继承当前 Contract Version；
- 复用已验证 Artifact；
- 不复用失效 Runtime Handle。

### 8.2 Reassign

- 释放旧 Claim；
- 创建新 Owner 与 Lease；
- 记录 Reassign Reason；
- 防止两个 Worker 同时持有同一写 Task。

### 8.3 Session Recovery

- `pi.appendEntry()` 保存 Run Snapshot；
- `session_start` 恢复纯数据；
- RPC Client 与 AgentSession 重新创建；
- 无法重新接管的 Child 标记为 Infrastructure Lost。

## 9. Completion Latch

### 9.1 触发条件

当 Required Files、Tests、Typechecks、Documentation 与 Gap Classification 均满足时，Run 进入 `SATISFIED`。

### 9.2 锁定行为

- 停止普通探索；
- 保留缺失 Live E2E；
- 保留 Commit；
- 保留 Final Report；
- 额外探索需要 Lead 解锁。

### 9.3 防止继续工作偏差

Completion Latch 解决“实现与检查已经通过，但 Worker 继续读取外围文件”的失控模式；高 Thinking Level 不得绕过 Latch。

## 10. Workflow Failure Salvage

Workflow 失败时保存：

- Completed Artifacts；
- Verified Artifacts；
- Interrupted Runs；
- Missing Deliverables；
- Integration State；
- Recovery Actions。

顶层 `failed` 不得抹平局部可用成果。

## 11. Hook Escape Path

阻止 Agent 停止或工具执行的 Hook 必须返回：

- 未满足条件；
- 当前允许动作；
- 最大重试次数；
- Finalize 或 Blocked 出口。

错误模式：

```text
Hook: 继续工作
Agent: 尝试完成
Hook: 继续工作
Agent: 再次尝试完成
```

正确模式：

```text
Hook: 缺少 question-default-consistency 的状态
Allowed: record_evidence 或 mark_unknown
Retries remaining: 1
Escape: BLOCKED
```

## 12. 生命周期不变量

- Task、Run 与 Session ID 不混用。
- Run Terminated 不等于 Task Verified。
- Agent Self-Completion 不等于系统接受。
- Budget Exhausted 先 Finalize 后 Abort。
- Session Replacement 后旧 Context 不可继续使用。
- Control Mutation 使用 Version 与 Command ID。
- Terminated Run 拒绝迟到 Mutation。
- 所有 Transition 产生 Durable Audit Event。
- Acceptance 满足后进入 SATISFIED 而非继续探索。
- Workflow Failure 必须生成可恢复成果清单。
