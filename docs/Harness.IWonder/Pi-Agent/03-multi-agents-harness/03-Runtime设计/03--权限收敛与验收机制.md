# 权限、收敛与验收机制

> [!abstract]
> 治理层把模型提出的候选动作放入确定性规则中执行，并把 Agent 自报完成放入独立验证中接受：Scope、权限、预算和文件所有权在 Tool 执行前后强制，Acceptance Contract 在执行前冻结，Reviewer 只判定冻结标准，Review/Rework 受轮次上限约束，最终以 Completed、Verified、Integrated 三段状态区分“提交、可信与落地”。

> **上层主题：** [有界证据侦察代理](../05-侦察代理产品原型层/01-有界证据侦察代理.md)

## 1. 治理层职责

治理层处理四类不可交给模型自觉遵守的规则：

- 安全边界；
- 成本边界；
- 文件并发边界；
- 质量验收边界。

```text
Agent proposes action
  ↓
Scope Gate
  ↓
Permission Gate
  ↓
Budget Gate
  ↓
Ownership Gate
  ↓
Tool executes
  ↓
Postcondition Gate
  ↓
Evidence / Artifact validation
```

## 2. Scope 与权限治理

### 2.1 Read Scope

- Canonical Path 必须匹配 Include；
- Exclude 与 Prohibited 优先；
- Symlink 在解析后校验；
- 敏感路径采用全局 Deny；
- Scope Change 需要 Contract Revision。

### 2.2 Write Scope

- Scout 与 Planner 的 Write Scope 为空；
- Worker 只写 Contract 声明路径；
- Reviewer 不修改被审查 Artifact；
- 多 Worker 写范围必须不重叠或使用 Worktree。

### 2.3 Command Policy

命令权限不能只靠 Prompt：

- Scout 不开放任意 Bash；
- Reviewer 只开放只读 Git 与指定测试；
- Worker Command 使用 Allowlist 或 Wrapper；
- Push、Credential 与生产操作默认 Deny；
- 危险动作要求 Human Approval。

### 2.4 Extension 权限

Tool Allowlist 只限制模型调用；Extension 代码仍拥有宿主权限，不可信 Extension 需要容器、沙箱或独立 OS User。

## 3. Budget 治理

### 3.1 Budget 维度

- Exploration Call；
- Total Tool Call；
- Unique Files Read；
- Files Modified；
- Wall-clock Time；
- Token Usage；
- Cost；
- Retry Count；
- Review Round；
- Rework Round。

### 3.2 计数规则

每个 Budget 必须提前定义：

- Protocol Tool 是否计入；
- 并行 Sibling Call 如何计入；
- Retry 是否重复消耗；
- Search 命中文件是否算 Read；
- Finalization 是否拥有保留预算；
- Compaction 与 Nested Model Usage 如何归集。

### 3.3 Soft 与 Hard Limit

- Soft Limit 产生 Milestone Warning；
- Hard Limit 触发 Finalizing；
- Finalization Deadline 超时触发 Abort；
- Lead 才能批准 Budget Revision。

>
> 基于 [失败轨迹](../00-Artifact/20260828-2-多代理协作能力研究札记——一次失败经历的复盘.md) 与 [经验验证](../09-经验验证层/01-失败轨迹与知识修订.md)，原“设置预算与验收标准即可收敛”补充为“验收满足后必须自动锁定探索，并区分权威验证与辅助诊断”。

### 3.4 Completion Latch

当 Required Acceptance 已满足时，治理层把 Run 标记为 `SATISFIED` 并关闭普通探索；只保留缺失 E2E、Commit 与 Final Report，额外探索需要 Lead 解锁。

## 4. Acceptance Freeze

### 4.1 冻结时点

Task 从 Ready 进入 Claimed 前冻结 Acceptance Contract。

```ts
interface AcceptanceContract {
  version: number;
  criteria: Criterion[];
  blockingSeverities: string[];
  requiredArtifacts: string[];
  requiredChecks: string[];
  frozenAt: number;
}
```

### 4.2 允许修改的条件

- 新发现 P0/P1 安全或数据风险；
- 原 Criterion 内部矛盾；
- 用户明确改变目标。

### 4.3 Scope Change Record

```yaml
scope_change:
  reason: 发现可复现的权限绕过
  evidence_ids: [ev-17]
  impact: 增加 AUTH-04 验收项
  approved_by: lead
  from_version: 2
  to_version: 3
```

任何 Reviewer 建议都不能隐式改变 Acceptance Version。

## 5. Reviewer 判定器模型

### 5.1 Reviewer 输入

- Frozen Acceptance Contract；
- Implementation Artifact；
- Test Artifact；
- Relevant Evidence；
- Previous Blocking Findings。

### 5.2 Reviewer 输出

```ts
interface ReviewFinding {
  findingId: string;
  criterionId?: string;
  severity: "P0" | "P1" | "P2" | "P3";
  classification: "blocking" | "advisory";
  evidence: EvidenceRef[];
  reproduction?: string;
  expected?: string;
  actual?: string;
  requiredFix?: string;
}
```

### 5.3 Blocking 条件

Finding 成为 Blocking 必须满足：

- 对应冻结 Criterion；或
- 具有可验证 P0/P1 风险；
- 提供明确 Evidence；
- 提供可执行复现或失败检查；
- Required Fix 保持在当前 Scope。

### 5.4 Advisory 条件

下列内容只能作为 Advisory：

- 风格偏好；
- 无关重构；
- 新产品需求；
- 理论优化；
- 无证据猜测；
- 超出当前 Contract 的改善项。

### 5.5 Reviewer Scope Gate

Reviewer 默认只读取 Changed Files、Directly Affected Interfaces、Acceptance-required Tests 与 Declared Packaging Artifacts；扩大范围必须提交 Path、Reason、Criterion 与 Expected Value，无法关联 Criterion 或 P0/P1 的外围发现不能阻塞当前任务。

## 6. Review 与 Rework 收敛

### 6.1 轮次上限

```yaml
convergence_policy:
  max_scout_rounds: 2
  max_review_rounds: 2
  max_rework_rounds: 2
```

### 6.2 Review 轮次语义

- Review 1 执行完整冻结范围审查；
- Review 2 只复验上一轮 Blocking Finding 与新增 P0/P1；
- Review 3 必须由 Lead 批准；
- 超限后进入 Lead Arbitration。

### 6.3 超限出口

- Accept With Known Risk；
- Split Follow-up Task；
- Reassign Worker；
- Declare Blocked；
- Declare Failed。

## 7. Completed、Verified 与 Integrated

### 7.1 Completed

Agent 已提交 Schema 合法 Deliverable。

### 7.2 Verified

确定性检查或 Reviewer 已证明 Deliverable 满足 Acceptance。

### 7.3 Integrated

Verified Artifact 已安全进入目标分支、文档库或运行环境。

### 7.4 Run-level Satisfied

`SATISFIED` 表示 Required Acceptance 已满足但 Final Artifact、E2E 状态或 Commit 尚未完成；它触发 Completion Latch，不替代 Task-level Completed。

### 7.5 Integration Deliverable

实现类任务必须提交 Implementation Diff、Focused Test、Package Typecheck、Root Typecheck、Live E2E Result or Blocker 与 Reviewed Commit；缺少 Commit 时只能标记 `IMPLEMENTED_NOT_INTEGRATED`。

```text
submit
  ↓
COMPLETED
  ↓
schema + tests + review
  ↓
VERIFIED
  ↓
merge / publish / register
  ↓
INTEGRATED
```

## 8. Known Risk

Lead 可以在不消灭所有未知的情况下完成目标：

```yaml
known_risk:
  issue: 高并发下 session refresh 尚未压力测试
  severity: P2
  reason_accepted: 不属于当前登录超时修复范围
  followup_task: perf-test-session-refresh
  accepted_by: lead
```

Known Risk 必须结构化、可追踪并与 Follow-up 关联。

## 9. Hook Escape Path

每个阻止完成的 Hook 同时提供：

- 当前缺少的 Criterion；
- Evidence 或 Artifact 缺口；
- 当前允许动作；
- Remaining Retries；
- Blocked 或 Impossible 出口。

Hook 不得无限返回模糊的“继续工作”。

## 10. 文件所有权与 Worktree

### 10.1 共享工作区

适合只读 Scout、Planner 与 Reviewer。

### 10.2 静态文件所有权

```yaml
frontend-worker:
  owns: apps/web/**
backend-worker:
  owns: services/api/**
test-worker:
  owns: tests/**
```

适合写范围天然分离的 Worker。

### 10.3 Worktree 隔离

适合：

- 修改公共核心文件；
- 多方案实验；
- 大规模重构；
- 独立回滚；
- Commit 级集成。

Worktree 解决文件隔离，不提供任务协调与消息通信。

## 11. Verification Authority

### 11.1 权威检查

验证按 Focused Tests、Package Typecheck、Root Typecheck、Packaging/Manifest、Live E2E 分层保存 Artifact。

### 11.2 辅助信号

LSP、Editor Warning、Symlinked Dependency Warning 与非权威 Static Hint 只提供诊断线索。

### 11.3 冲突处理

权威检查通过而辅助信号冲突时，记录 Environment Anomaly 并停止反复修改已通过代码；必要时交给 Lead 仲裁。

## 12. 全局完成判定

Lead 只回答封闭问题：

1. Required Tasks 是否 Verified？
2. Required Artifacts 是否 Integrated？
3. Automated Gates 是否通过？
4. 是否存在未处理 P0/P1？
5. Review 与 Rework 是否超限？
6. 剩余问题属于 Blocker、Known Risk 还是 Follow-up？

合法全局终态：

- `GOAL_ACHIEVED`；
- `GOAL_ACHIEVED_WITH_KNOWN_RISKS`；
- `BLOCKED`；
- `FAILED`。

## 13. 治理层原则

- 模型提出动作。
- Policy 决定动作是否允许。
- Agent 提交完成。
- Verification 决定系统是否接受。
- Reviewer 判定冻结标准。
- Lead 接受风险与宣告目标终态。
- Harness 保证所有循环拥有上限和出口。
- Acceptance 满足后由 Completion Latch 阻止继续工作偏差。
- Verification Signal 必须声明权威层级。
- Commit 与 E2E 状态属于正式交付物。
