# 多代理支撑系统架构

> [!abstract]
> 多代理 Harness 是围绕概率性 Agent 建立的确定性运行系统：控制面决定任务与收敛，执行面隔离角色与上下文，状态面保存事实与进度，治理面阻止越权并验证交付；四个平面共同把一次自然语言委派转化为可调度、可观察、可恢复、可终止和可验收的工程过程。

> [!note]
> **上层主题：** [Pi 拓展运行时基础](../01-Pi拓展支撑层/01-Pi拓展运行时基础.md)

## 1. Harness 的系统定位

模型负责局部判断，Harness 负责运行秩序。

```text
User Intent
  ↓
Lead Interpretation
  ↓
Task Contract
  ↓
Controlled Execution
  ↓
Durable Evidence
  ↓
Verification
  ↓
Integrated Result
```

Harness 需要确保：

- 输入目标被转化为有限任务；
- 每个角色只获得所需上下文与能力；
- 执行动作经过确定性门禁；
- 中间事实不依赖聊天记忆；
- 预算、失败与停止拥有明确协议；
- Agent 自报完成不直接成为系统完成。

## 2. 四平面架构

### 2.1 控制面

控制面回答“谁在何时做什么，以及何时停止”。

核心组件：

- Lead Agent；
- Task Planner；
- Parallelism Gate；
- Scheduler；
- Contract Manager；
- Run Supervisor；
- Convergence Controller。

核心输入：

- 用户目标；
- 当前项目状态；
- Task Dependency；
- Budget 与风险策略；
- 已完成 Artifact。

核心输出：

- Task Contract；
- Role Assignment；
- Start、Steer、Finalize 与 Abort Command；
- Scope Change Decision；
- Goal Terminal Decision。

### 2.2 执行面

执行面回答“Agent 如何在明确边界内完成局部工作”。

```text
Execution Plane
  ├─ Scout Runtime
  ├─ Planner Runtime
  ├─ Worker Runtime
  └─ Reviewer Runtime
```

每个 Runtime 拥有：

- 独立 AgentSession；
- 独立 Context Window 与受控共享的 Verified Context Capsule；
- Role Prompt；
- Task Contract；
- Role Extension；
- Role Skills；
- Active Tools；
- Runtime Policy。

### 2.3 状态面

状态面回答“系统依靠什么事实恢复和决策”。

```text
State Plane
  ├─ Task Registry
  ├─ Run Registry
  ├─ Evidence Store
  ├─ Artifact Store
  ├─ Mailbox
  └─ Git / Worktree State
```

状态面不依赖模型上下文保持一致性；模型可以读取状态快照，但不能通过自然语言直接改写权威状态。

### 2.4 治理面

治理面回答“候选动作是否允许，以及交付是否可信”。

```text
Agent proposes action
  ↓
Scope Policy
  ↓
Permission Policy
  ↓
Budget Policy
  ↓
Tool execution
  ↓
Evidence Validation
  ↓
Acceptance Verification
```

治理对象：

- 文件访问；
- 命令执行；
- Budget 消耗；
- Scope 漂移；
- Deliverable 完整性；
- Test 与 Review 结果；
- Completion Transition。

## 3. 四平面之间的契约

### 3.1 Control → Execution

控制面通过 Task Contract 下发：

- Objective；
- Scope；
- Questions；
- Deliverables；
- Acceptance；
- Budget；
- Stop Conditions；
- Escalation Policy。

### 3.2 Execution → State

执行面只能通过结构化接口提交：

- Evidence Record；
- Observation Outcome；
- Artifact Reference；
- Progress Event；
- Blocked Reason；
- Terminal Report。

### 3.3 Governance → Execution

治理面通过 Hook 与 Tool Wrapper：

- Allow；
- Deny；
- Rewrite；
- Require Approval；
- Force Finalization；
- Abort。

### 3.4 State → Control

状态面向 Lead 提供：

- Task Snapshot；
- Run Snapshot；
- Question Coverage；
- Remaining Budget；
- Blocking Dependencies；
- Verified Artifacts；
- Known Risks。

## 4. Task Contract 作为协作 API

### 4.1 Contract 结构

```yaml
task_id: scout-auth
contract_version: 1
role: scout

objective:
  定位登录超时问题涉及的代码路径

scope:
  read:
    - src/auth/**
    - tests/auth/**
  write: []
  prohibited:
    - 修改生产代码
    - 扩展到密码策略重构

questions:
  - id: timeout-definition
    text: 超时值在哪里定义？
  - id: session-refresh
    text: 哪些路径会刷新 session？
  - id: default-consistency
    text: 是否存在不一致的默认值？

deliverables:
  - evidence-table
  - call-chain
  - candidate-causes
  - unknowns

budget:
  max_exploration_calls: 12
  max_files_read: 20
  max_minutes: 10

stop_when:
  - all_questions_resolved
  - two_consecutive_low_yield_cycles
  - any_hard_budget_exhausted
  - external_blocker
```

### 4.2 Contract 的边界语义

- Objective 定义有限目标；
- Scope 定义访问边界；
- Questions 定义知识边界；
- Deliverables 定义交付边界；
- Acceptance 定义验证边界；
- Budget 定义成本边界；
- Stop Conditions 定义终止边界。

### 4.3 Contract Revision

执行期间的目标变化必须形成新版本：

```yaml
revision:
  from_version: 1
  to_version: 2
  reason: 发现明确的跨模块刷新路径
  evidence_ids: [ev-07]
  approved_by: lead
  changes:
    scope.read:
      add: [src/session/**]
```

Revision 使用 `expected_version` 防止 Lead、Supervisor 与 Subagent 对不同版本进行并发修改。

## 5. 角色责任边界

### 5.1 Lead

- 解释目标；
- 冻结 Contract；
- 分配角色；
- 处理 Scope Change；
- 决定追加预算；
- 接受剩余风险；
- 宣告全局终态。

### 5.2 Scout

- 定位事实；
- 收集 Evidence；
- 回答有限 Questions；
- 标记 Unknown；
- 提交候选原因；
- 不设计完整实现。

### 5.3 Planner

- 消费 Verified Evidence；
- 生成可执行步骤；
- 标明文件与风险；
- 不修改代码；
- 不重新扩大目标。

### 5.4 Worker

- 按 Plan 修改文件；
- 运行指定验证；
- 提交 Diff 与 Test Artifact；
- 不改变 Acceptance Contract。

### 5.5 Reviewer

- 对照冻结标准判定；
- 区分 Blocking 与 Advisory；
- 验证证据与复现；
- 不把偏好升级为阻塞条件；
- 不宣告全局目标完成。

## 6. 上下文装配模型

```text
Agent Context
  = Role Prompt
  + Task Contract
  + Stable Project Instructions
  + Verified Context Capsules
  + Handoff ACK State
  + Relevant Repository Slice
  + Skill Descriptions
  + Active Tool Definitions
  + Permission Policy Summary
```

上下文装配规则：

- 稳定规则进入项目 Context；
- 单次事实进入 Task Contract；
- 大型成果进入 Artifact；
- Lead 消息只传控制与摘要；
- 原始日志不复制到多个 Agent；
- 依赖 Artifact 按需读取；
- 下游先 ACK 上游 Artifact 再声明 Context Gap；
- Context Gap 之外的重复侦察计入 Context Tax。

## 7. 状态与消息分工

| 内容 | 权威载体 | 消息中的表达 |
| :-- | :-- | :-- |
| Task 状态 | Task Registry | Task ID + 状态摘要 |
| Run 状态 | Run Registry | Run ID + Milestone |
| Evidence | Evidence Store | Evidence ID + 核心 Claim |
| 大型报告 | Artifact Store | Path + 摘要 |
| 代码修改 | Git / Worktree | Commit + Diff 摘要 |
| 协调请求 | Mailbox | 完整结构化消息 |

聊天记录只提供叙事，不承担一致性、并发控制与崩溃恢复。

## 8. 完成语义

```text
Agent submits deliverable
  ↓
Task COMPLETED
  ↓
Schema and evidence validation
  ↓
Task VERIFIED
  ↓
Artifact integration
  ↓
Task INTEGRATED
```

全局目标完成条件：

- 所有 Required Task 均 Verified；
- 必需 Artifact 均 Integrated；
- 自动化质量门通过；
- 无未处理 P0/P1；
- 用户目标均对应交付物；
- Known Risks 已由 Lead 接受或拆分 Follow-up。

## 9. 并行度门禁

```text
Parallelism Value
  = Independent Workstreams
  × Work per Stream
  + Independent Perspective Value
  - Context Reacquisition Cost
  - Artifact Conversion Cost
  - Coordination Cost
  - Duplicate Verification Cost
  - File Conflict Risk
  - Integration Cost
```

适合并行：

- 至少两个独立方向；
- 每个方向工作量足够；
- 文件或 Artifact 边界清晰；
- 结果可独立验证。

不适合并行：

- 后续步骤强依赖前序结果；
- 多个 Agent 修改同一核心文件；
- 任务规模很小；
- 必须持续共享完整上下文；
- 缺少客观验收标准。

## 10. 经验轨迹带来的架构修订

真实失败表明，四平面模型仍然成立，但平面间缺少三个关键协议：

### 10.1 Context Capsule

Execution Plane 不能只提交自由文本报告；它需要提交带 Scope、Provenance、Coverage、Confidence 与 Content Hash 的 Context Capsule。

### 10.2 Handoff Acceptance

State Plane 保存 Artifact 不代表下游已经采用；下游必须显式 ACK 已接受事实、拒绝事实与 Context Gap。

### 10.3 Completion Latch

Governance Plane 在 Acceptance 已满足时自动锁定普通探索，只允许缺失验证、Commit 与 Final Report。

### 10.4 Failure Salvage

Control Plane 在 Workflow Failure 时保全 Completed 与 Verified Artifacts，并生成 Recovery Actions，而非把局部成果折叠为单一 failed。

### 10.5 Transport 边界

SDK、RPC 与 Intercom 只解决传输；Task Contract、Shared State、Acceptance 与 Integration 才构成协调系统。

## 11. 架构决策

- Lead 管意图、边界与收敛。
- Subagent 管有限局部执行。
- Contract 是协作 API。
- Registry 是状态事实源。
- Artifact 承载大型成果。
- Message 承担协调通知。
- Hook 执行不可违反规则。
- Verification 决定系统接受。
- Worktree 处理文件并发隔离。
- Harness 对预算与终止性负责。
